# 13. 리포트 · 성장 추적

> ⚠️ **리포트 계약 문서가 아직 도착하지 않았습니다.**
> AI 파트에서 작성 중이며 9/3 목요일 회의 전 전달 예정입니다.
> 이 문서에는 **현재까지 확정된 것만** 담았습니다.
> 계약 도착 후 `02-database.md` 의 리포트 스키마와 함께 갱신하세요.

---

## 확정된 것

### 평가 3축

```
내용   답변의 논리성, 구체성, 질문 관련성
음성   발화 속도, 필러워드, 침묵
시선   화면 응시 비율, 이탈 횟수
```

### ★ 부분 실패 처리

세 축은 독립적으로 처리되지만 **내용 관련성이 총점 게이트 역할**을 합니다.
주제에서 벗어난 유창한 답변이 음성·시선 점수만으로 높은 총점을 받는 것을 막는
장치입니다.

| 축 | 실패 시 |
|---|---|
| **내용 분석** | **전체 실패 처리.** 총점을 낼 수 없음 |
| 음성 분석 | 해당 축만 "결과 없음"으로 표시 |
| 시선 분석 | 해당 축만 "결과 없음"으로 표시 |

즉 음성·시선이 실패해도 리포트 자체는 생성되고, 해당 섹션만 비어 있습니다.
프론트는 축 단위로 "분석 실패" 상태를 렌더링할 수 있어야 합니다.

### 회차 비교

- 비교 대상은 `is_replay == true` 인 질문뿐입니다. [`12-replay.md`](./12-replay.md)
- 점수 비교는 **직전 회차 기준**입니다
- 회차 수 제한은 없습니다
- 질문 세트가 1회차로 고정되어 있으므로 임의의 두 회차를 비교할 수 있습니다

## 계약 도착 시 확인할 것

| # | 항목 | 왜 필요한가 |
|---|---|---|
| 1 | 점수 스케일 (0~100? 1~5?) | 축마다 다를 수 있음 |
| 2 | 작업 등록·폴링 방식이 질문 생성과 같은지 | `AiClient` 재사용 여부 |
| 3 | 리포트 생성 소요 시간 | 타임아웃 값 |
| 4 | 진행률(`stage`) 값 목록 | WebSocket push 매핑 |
| 5 | 부분 실패를 응답에서 어떻게 표현하는지 | 필드명, 실패 축 목록 |
| 6 | 재시도 시 실패한 축만 재요청 가능한지 | 비용·시간 절약 |
| 7 | 회차 비교 응답 형식 | AI가 계산해주는지, Spring이 하는지 |
| 8 | 결과 JSON 전체 스키마 | 엔티티 설계 |

**7번이 특히 중요합니다.** AI가 짝지어 계산해서 주는지, Spring이 두 회차 데이터를
꺼내 직접 계산하는지에 따라 `growth` 모듈의 크기가 완전히 달라집니다.

## 예상 흐름 (미확정, 참고용)

```
session_end 수신
  → status = completed
  → AI에 리포트 생성 요청 (POST /ai/reports 또는 유사)
  → task_id 폴링
  → 결과 저장
  → WebSocket으로 "리포트 준비 완료" push
```

질문 생성과 같은 폴링 구조라면 `infrastructure/ai/` 의 폴링 로직을 그대로
재사용할 수 있습니다. **폴링·타임아웃·에러 분류를 리포트에도 쓸 수 있게
일반화해서 설계해두세요.**

## 작업 순서

리포트는 **3단계** 작업입니다. 세션·질문·재연습이 동작한 뒤에 착수합니다.
[`90-open-questions.md`](./90-open-questions.md) 의 일정 참고.

지금 할 수 있는 것:

- `infrastructure/ai/` 폴링 로직을 리포트에도 쓸 수 있게 제네릭하게 설계
- `report` 모듈 패키지만 만들어두기
- 엔티티는 계약 도착 후 작성 (미리 만들면 버릴 가능성이 높음)
